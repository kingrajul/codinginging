📖 What is SSL Stripping?

Even if your site supports HTTPS, the very first request a user makes is usually plain HTTP (they type example.com, not https://example.com). The server responds with a redirect to HTTPS — but that redirect travels over the unencrypted HTTP connection first.

An attacker positioned between the victim and the internet (public Wi-Fi, rogue access point, compromised router) can intercept that redirect and replace it, keeping the victim on HTTP indefinitely. This is SSL stripping.

Without HSTS, the browser has no way to know that it should always use HTTPS before it sees the first response from the server.

🔴 The Attack — Man-in-the-Middle on HTTP

Traffic flow without HSTS (victim on a café Wi-Fi controlled by attacker):

Browser ──────→ [HTTP] GET http://bank.example/ ──────→ Attacker
Attacker forwards as HTTPS to real server, receives 302 → HTTPS
Browser ←────── [HTTP] 200 OK — stripped, no HTTPS ←────── Attacker
Victim sees "http://" but page looks normal — attacker reads all traffic
  1. 1Attacker sets up an ARP spoofing or rogue Wi-Fi access point to intercept traffic.
  2. 2Tools like sslstrip (by Moxie Marlinspike) automate the attack: they proxy HTTPS upstream but serve HTTP downstream.
  3. 3The victim's browser shows a padlock-free http:// URL; credentials and session cookies sent in POST/cookies flow in plaintext.
  4. 4Attacker captures login form data, session tokens, credit card numbers — everything sent over the downgraded connection.

Run the demo locally (requires a network interface in promiscuous mode):

# Install sslstrip (Kali Linux / Parrot OS)
sudo apt install sslstrip arpspoof

# Enable IP forwarding
echo 1 | sudo tee /proc/sys/net/ipv4/ip_forward

# Redirect port 80 traffic through sslstrip
sudo iptables -t nat -A PREROUTING -p tcp --dport 80 -j REDIRECT --to-port 10000

# ARP-spoof the victim (replace IP addresses)
sudo arpspoof -i eth0 -t 192.168.1.100 192.168.1.1 &

# Start sslstrip
sudo sslstrip -l 10000

(Only perform this on networks you own or have explicit permission to test.)

✅ The Fix — Strict-Transport-Security (HSTS)

HSTS tells the browser: "For the next N seconds, always connect to me via HTTPS — refuse to load this site over HTTP even if asked."

Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

Directive breakdown:

  • max-age=31536000 — remember this for 1 year (recommended minimum).
  • includeSubDomains — apply to all subdomains too (prevents stripping on login.example.com).
  • preload — opt in to the browser preload list (see below).

In Nginx (must only be sent over HTTPS connections):

server {
    listen 443 ssl;
    ...
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" always;
}

HSTS Preloading solves the "first visit" problem: even before the browser has ever seen the HSTS header, preloaded domains are hardcoded into Chrome, Firefox, Safari, and Edge to always use HTTPS. Submit your domain at hstspreload.org.

Traffic flow with HSTS:

Browser ──→ [Browser upgrade] https://bank.example/ — HTTPS before any network packet
Attacker can't intercept — TLS established end-to-end
Educational demo — do not use in production.
